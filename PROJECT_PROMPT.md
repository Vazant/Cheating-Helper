# Рабочий промпт проекта (черновик)

## Роль исполнителя

Развивать форк проекта Cheating Daddy итеративно и только по подтверждённым требованиям пользователя. Не принимать продуктовые решения при неоднозначности: фиксировать вопрос, останавливать зависимую работу и запрашивать уточнение.

## Цель первого этапа

1. Создать GitHub-форк подтверждённого исходного репозитория Cheating Daddy.
2. Подготовить локальную рабочую копию форка.
3. Добавить Groq API и подтверждённый пользователем набор актуальных моделей.
4. Добавить получение данных об использовании токенов, если API их предоставляет.
5. Выводить предупреждение при приближении к подтверждённому пользователем лимиту.

## Уточнённая цель первой реализации

1. Сначала составить карту фактического назначения каждой модели: live-аудио/транскрипция, текстовый ответ, анализ изображения/экрана, local AI.
2. Добавить в настройки независимый выбор модели для каждой поддерживаемой функции; не показывать модель в роли, которую она технически не поддерживает.
3. Заменить отключённый `qwen/qwen3-32b` только после подтверждения назначения и совместимости замены.
4. Для Groq предложить актуальные бесплатные текстовые модели, включая `openai/gpt-oss-20b` и `openai/gpt-oss-120b`, с понятным default/fallback.
5. Удалить фиктивный подсчёт квот по символам и использовать документированные HTTP rate-limit headers.
6. Предупреждать в консоли при использовании 95% RPD или TPM и корректно объяснять 404/429.
7. До изменения кода провести анализ сабагентами и получить подтверждение плана пользователя.

## Подтверждённые решения реализации

- Hosted Text default: `openai/gpt-oss-120b` (качество).
- Selectable Groq text models: `openai/gpt-oss-120b`, `openai/gpt-oss-20b`, `qwen/qwen3.6-27b`.
- Настройки показывают группы только активного режима Hosted/Local; неактивные значения сохраняются.
- Первый кодовый этап ограничен Hosted Text selector, Groq fallback, реальными RPD/TPM, 95% warnings, streaming и понятными ошибками.
- Google Gemma пока остаётся кодом совместимости, но не участвует в Groq selector и автоматическом cross-provider fallback.
- Fallback внутри Groq автоматически логируется: 404 может пройти оставшиеся модели в стабильном порядке качества; 429 переключает только на следующий настроенный ключ и прекращает запрос после однократной проверки каждого ключа; 401/403, network и 5xx ничего не переключают.
- Отсутствующий Groq key должен давать явное предупреждение; скрытый переход на Google запрещён для выбранной Groq-модели.
- Vision/Live Audio selectors — отдельные этапы после Hosted Text.
- Local Vision планируется отдельно: `qwen3-vl:4b` рекомендуемая, `qwen3-vl:2b` облегчённая, `gemma3:4b` совместимая; фактический выбор только после проверки Ollama capability `vision`.
- Hosted Vision позже может использовать текущий Google path или Groq `qwen/qwen3.6-27b`; невидимый hosted↔local fallback запрещён.

## Правила выполнения

- Перед реализацией неоднозначного требования задать пользователю вопрос.
- Не добавлять функции, зависимости и архитектуру «на будущее» без отдельного требования.
- Каждая работа ведётся в отдельном файле в `tasks/`.
- Работа считается завершённой только когда выполнены все подзадачи, критерии приёмки и проверки.
- Если проверка не пройдена, вернуть статус `IN_PROGRESS`, записать результат проверки и продолжать исправления до полного прохождения.
- Секреты и API-ключи не коммитить; использовать существующий механизм конфигурации проекта.
- После каждого этапа сохранять фактический результат и доказательство проверки в соответствующем файле задачи.
- Сабагенты на исследовательском этапе работают read-only и сохраняют вывод через главного агента.
- Не смешивать в одной настройке текстовые, vision, live-audio и transcription модели.
- Не добавлять SDK, если существующий `fetch` покрывает API корректно.

## Новое требование: бесплатный Gemini и несколько Groq keys

- Gemini временно полностью отключается: поле ключа и запуск hosted Gemini недоступны, сохранённый старый ключ не используется.
- Несколько Groq keys предназначены для ручного управления принадлежащими пользователю ключами, а не для обхода organization/project limits.
- Пользователь подтвердил владение всеми Groq keys и просит последовательное переключение на следующий ключ при исчерпании доступной квоты.
- Пользователь явно разрешил локальное хранение Groq keys без OS-backed шифрования на этом этапе.
- Ротация должна быть ограниченной, не зацикливаться, не выводить secrets и останавливаться после проверки всех настроенных ключей.
- Детализация и критерии проверки находятся в `tasks/010-gemini-free-tier-guard.md` и `tasks/011-groq-multiple-keys.md`.

## Предлагаемый этап без Gemini: Groq Audio и Vision

- Hosted audio строится как отдельные стадии: `whisper-large-v3-turbo` выполняет Speech-to-Text, затем выбранная text LLM (`openai/gpt-oss-120b` default) формирует ответ.
- GPT-OSS является text-only и не должен называться или использоваться как аудио/vision model.
- Hosted screenshots обрабатывает отдельная vision-capable `qwen/qwen3.6-27b` с явной пометкой Preview.
- Для screenshots хранить отдельный редактируемый `screenAnalysisPrompt`; конкретный ручной вопрос добавлять отдельно.
- В Vision-запрос добавлять последние две текстовые реплики разговора как text-only context; предыдущие изображения повторно не отправлять.
- `openai/gpt-oss-120b` не является vision fallback и не получает image payload; он может обрабатывать только текстовый результат успешного vision stage.
- Whisper API принимает file/chunk POST, а не текущий Gemini Live stream; использовать VAD и отправлять законченную реплику как WAV 16 kHz mono.
- Settings разделяют STT, response LLM и vision model; модели не показываются в несовместимых ролях.
- Реализация начинается только после подтверждения вопросов в `tasks/012-groq-audio-vision.md`.
